# A Little Love Letter

The website is static and can be hosted on GitHub Pages. Visitor records and administrator sign-in use Supabase because GitHub Pages does not run server-side code.

## Supabase setup

1. Create a Supabase project.
2. In [`supabase/setup.sql`](supabase/setup.sql), confirm the email in both read policies matches the email you will use to administer the site. Run the entire SQL file in the SQL Editor of the project whose URL is in `visitor-config.js`. It creates/updates `public.visits`, creates `public.gallery_password_attempts`, restricts writes to the Edge Function service role, and allows only that signed-in email to read either table.
3. In **Authentication** settings, turn off public sign-ups. Create and confirm your administrator user with that same email in the Supabase dashboard. Do not create any other accounts.
4. Copy your Supabase project URL and its **publishable** key (or legacy `anon` key) into [`visitor-config.js`](visitor-config.js). These are intended to be public browser values. Never put a `service_role` or secret key in this file.
5. Keep the `visits` table policies from the SQL setup in place. Do not add public `SELECT`, `UPDATE`, or `DELETE` policies.
6. Install the [Supabase CLI](https://supabase.com/docs/guides/cli), sign in, and link this folder to the same project. Deploy the event logger with JWT verification disabled because it accepts anonymous site events:

	```sh
	supabase login
	supabase link --project-ref <your-project-ref>
	supabase functions deploy log-activity --no-verify-jwt
	```

	The function uses Supabase's server-side `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` environment variables. Never put the service-role key in browser code. It accepts only an event type and broad device/browser category; the entered gallery password is never sent. It gets the IP address from the request's proxy headers.

The dashboard is at `/admin/` on your site. Sign in there with the administrator email and password created in Supabase. The dashboard keeps its access token in the current browser tab's session storage and supports token refresh; it does not put an admin password in the repository.

## Publish on GitHub Pages

1. Upload the project files, including the `admin` and `100k-love` folders, `visitor-config.js`, and `I love you prema!-2.txt` to your repository's publishing branch. Keep the text file in the same root folder as `index.html`; the archive page loads all 100,000 lines from it.
2. In the repository, open **Settings → Pages** and choose the branch and folder containing `index.html`.
3. Once published, open `https://<username>.github.io/<repository>/admin/` to sign in. For a custom domain, use `https://<your-domain>/admin/`.

The publishable/anon key in `visitor-config.js` is not an admin password. Database row-level security allows visitor reads only to the email allowlisted in the SQL policy. Anyone can see a static dashboard's HTML, but other accounts cannot read the visitor table. Do not add a Supabase secret or `service_role` key to the site.

## Visitor data

The site records the visit time generated by the database, a broad device/browser category (for example `Android phone / Chrome`), a device model when the browser exposes one, and the request IP address. A visit is recorded once per browser tab session when browser storage is available. The full user-agent string is only inspected in the visitor's browser to derive these labels; it is not sent to or stored. Failed gallery password submissions are recorded separately with time, category, available model, and IP; the attempted password is never logged. Exact models are unavailable on some browsers/devices (for example, iOS Safari may not expose them). Names and location are not collected. IP addresses and device models can be personal data: disclose this collection to visitors, restrict dashboard access, and set a retention period appropriate to your use. Times are displayed in the administrator's local timezone.

The event endpoint is public so the static site can report activity. It does not expose the service-role key, and database reads remain administrator-only, but a person could send fabricated events or flood the log. Treat the records as basic activity/security signals, not fraud-proof analytics; add rate limiting and retention controls before relying on them for abuse-sensitive decisions.

To preview the static pages locally, run `py -m http.server 8000` from this folder and open `http://127.0.0.1:8000`. Visit recording will work after the Supabase URL and publishable key are configured.
